# Stitch 前端重构交接说明

最后更新：2026-04-21

## 1. 文档目的

本文档不是开发实现方案，也不是接口文档。

它的目标是把当前项目的真实业务定位、页面职责、角色权限、关键链路、状态要求和非目标整理清楚，便于 Stitch 基于真实系统做前端重构设计。

Stitch 需要据此完成：

- 信息架构设计
- 页面层级设计
- 关键页面布局设计
- 页面间跳转关系设计
- 医疗工作台风格统一
- 关键状态与提示的交互表达

Stitch 不应擅自改变：

- 系统业务边界
- 主流程闭环
- 角色权限边界
- 页面模块职责
- 后端接口语义

## 2. 项目定位

本项目是“慢病辅助诊疗业务系统”，不是完整 HIS，也不是完整 EMR。

核心目标：

- 提供接近真实医院工作站的慢病管理工作台
- 支持登录、工作台、患者详情、预测建议、随访、档案、治理等业务闭环
- 将业务能力与模型能力共存，但边界清晰
- 让系统既能演示，又能继续扩展

明确不做：

- 收费、结算、医保全流程
- 住院、床位、医嘱全流程
- 药房库存、采购、出入库
- 完整处方系统
- 医生主流程中的 CSV 导入
- 医生主流程中的模型训练中心

## 3. 当前真实前端入口

当前 canonical 前端以 Vue Router 为准，不以历史备份页、simple 页、legacy 页为准。

真实入口：

- 登录页：`/login`
- 业务壳层：`/`

当前主要路由：

- `/login`
- `/`
- `/patient-detail/:patientId?`
- `/nurse-followups`
- `/model-insight`
- `/model-dashboard`
- `/governance`
- `/drug-management`
- `/drug-permission-management`

Stitch 设计时必须以这些真实路由和页面职责为基础，而不是凭想象补一个“全新站点”。

## 4. 当前主闭环

当前项目已经补通并验证的最小主闭环是：

1. 登录
2. 进入工作台
3. 打开患者详情
4. 在患者详情页触发真实预测
5. 展示最新预测结果
6. 退出登录回到 `/login`

这条闭环是 Stitch 设计时最优先要服务的主流程。

换句话说，整个前端重构必须优先保证这条链路更清晰、更稳、更像真实工作站，但不能把它拆散。

## 5. 角色与工作台

当前前端登录角色主要有三类：

- doctor
- nurse
- archivist

### 5.1 doctor

可访问模块：

- 医生首页
- 患者档案
- 药品管理
- 药品权限管理
- 模型看板
- 模型洞察
- 治理看板
- 系统中心

医生角色的核心任务：

- 查看待处理患者
- 打开患者详情
- 查看档案、时间线、附件、用药信息
- 触发模型预测
- 查看建议摘要
- 打开随访入口

### 5.2 nurse

可访问模块：

- 随访工作台
- 联系记录
- 流程看板
- 系统中心

护士角色的核心任务：

- 查看待随访任务
- 记录联系情况
- 推进随访流程

### 5.3 archivist

可访问模块：

- 患者档案
- 药品管理
- 药品权限管理
- 数据治理
- 治理看板
- 系统中心

档案员核心任务：

- 维护患者档案
- 查看档案与治理信息
- 管理药品和药品权限

## 6. 页面职责边界

### 6.1 登录页

页面目标：

- 账号登录
- 注册入口
- 健康状态展示

页面不应承载：

- 工作台内容
- 模型看板内容
- 治理中心内容

设计建议给 Stitch：

- 登录页要独立于业务壳层
- 应体现系统的医疗工作站属性，而不是普通管理后台或营销页
- 可显示系统状态、运行模式、模型可用性

### 6.2 业务壳层

当前壳层职责：

- 左侧导航
- 顶部状态栏
- 当前患者上下文
- 单一主内容区
- 全局消息状态
- 退出登录

设计要求：

- 一个导航项对应一个主内容区
- 主内容区互斥显示
- 不允许长页面堆叠多个模块伪装成切页
- 不允许多个 workspace 同时挂载在主内容区

### 6.3 医生首页

当前真实职责：

- 待处理患者队列
- 当前患者摘要
- 风险提示
- 打开患者详情
- 打开随访任务
- 打开患者档案

设计原则：

- 医生首页是入口摘要页，不是完整详情页
- 不要把患者详情、治理页、模型大看板堆到首页
- 首页应该帮助用户快速选患者、看风险、进入下一步动作

### 6.4 患者详情页

这是当前系统最核心页面。

当前真实职责：

- 患者主信息
- 电子档案摘要
- 附件面板
- 病程时间线
- 证据摘要
- 模型建议摘要
- 当前用药与用药评估
- 随访入口

当前最关键交互：

- 页面初始可能显示 `Preloaded Summary`
- 这只是预置摘要，不代表已经调用真实预测
- 用户点击 `Run Prediction` 后，页面才会调用真实 `POST /api/predict`
- 返回后页面切换到 `Latest Prediction`
- 如果失败，页面显示 `Prediction Failed`

Stitch 在设计时必须明确表达这几种状态：

- Preloaded Summary
- Predicting
- Latest Prediction
- Prediction Failed

避免误导用户“页面一打开就已经完成真实预测”。

### 6.5 患者档案页

当前职责：

- 患者身份信息
- 联系方式
- 紧急联系人
- 档案状态
- 建档信息
- 电子档案入口

不应承载：

- 模型训练
- 模型全局指标
- 全局治理总览

### 6.6 附件 / 电子档案

当前职责：

- 患者照片
- 身份证照片
- 医保卡照片
- 转诊单
- 检查报告
- 知情同意书
- 上传记录

设计要求：

- 区分患者照片与证件/单据附件
- 支持缩略图与预览
- 需要体现上传时间、上传人、附件类型

### 6.7 随访工作台

当前职责：

- 待随访任务
- 联系记录
- 随访状态
- 完成/关闭任务
- 下次计划

设计重点：

- 看板式工作流体验
- 联系记录录入清晰
- 状态推进明确

### 6.8 药品管理

当前职责：

- 药品目录
- 通用名 / 品牌名
- 剂型规格
- 单位
- 是否处方药
- 是否管制药
- 状态维护

不应扩展成：

- 库存管理
- 采购系统
- 药房出入库

### 6.9 药品权限管理

当前职责：

- 角色级药品权限矩阵
- 查看权限
- 开立权限
- 审核权限
- 执行权限
- 管制药权限

### 6.10 模型洞察

当前定位：

- 面向“当前患者”的模型结果页

应展示：

- 当前患者预测结果
- Top-K 风险事件
- 证据摘要
- 建议来源
- 模型降级状态
- 与当前患者相关的下一步动作

不应展示：

- 全局训练任务列表
- 全局模型版本总览
- CSV 导入入口

### 6.11 模型看板

当前定位：

- 面向模型治理与监控

应展示：

- 模型版本
- 最近训练时间
- MRR
- Hits@1 / Hits@10
- 调用量
- 回退比例
- 模型健康状态

不应展示：

- 当前患者详情
- 当前患者建议卡片

### 6.12 治理中心

当前定位：

- 面向数据质量和治理动作

应展示：

- 数据质量概览
- 缺失字段
- 异常时间线
- 待补全档案
- 冲突记录
- 治理动作

不应展示：

- 当前患者预测结果
- 模型训练总览

## 8. 关键状态与交互约束

### 8.1 登录态

必须支持：

- 未登录进入 `/login`
- 已登录访问受保护页
- 401 后清 session 并跳回登录页
- 主动退出后立即收口到 `/login`

### 8.2 预测态

必须区分：

- 未触发预测时的预置摘要
- 正在调用真实预测时的 loading
- 最新预测结果已返回
- 预测失败
- 模型不可用 / demo 模式 / 相似病例回退

### 8.3 权限态

必须支持：

- 无权限模块不可访问
- 不同角色的导航和主内容区不同
- 页面内出现 no permission 态时要明确

### 8.4 数据源 / 模型状态

页面最好能体现：

- 当前是 demo 模式还是 mysql 模式
- 当前模型是否降级或不可用

## 9. Stitch 设计时最应该优先做好的页面

按优先级建议 Stitch 优先设计：

1. 登录页
2. 业务壳层
3. 医生首页
4. 患者详情页
5. 随访工作台
6. 药品管理 / 药品权限管理
7. 模型洞察
8. 模型看板
9. 治理中心

如果时间有限，最先必须打磨好的其实只有前四项，因为它们直接决定系统主闭环能不能被感知为“真实可用”。

## 10. 给 Stitch 的视觉方向建议

这部分是方向，不是强制样式稿。

推荐方向：

- 真实医院工作站感
- 稳定、克制、专业
- 信息层级清楚
- 大量结构化信息可读
- 支持长时间使用
- 面向桌面端优先，同时兼容笔记本

不推荐方向：

- 营销页风格
- 过强渐变与装饰
- 夸张动效
- 普通 SaaS 后台模板感
- 把所有模块做成同质化卡片瀑布流

关键词建议：

- clinical workstation
- chronic disease management
- hospital desktop console
- structured information hierarchy
- professional, calm, operational

## 11. 给 Stitch 的硬约束

Stitch 设计时必须遵守：

- 不重定义项目为 HIS
- 不扩出收费、住院、库存、医保等模块
- 不把模型训练、CSV 导入塞回医生主流程
- 不把医生首页做成超长综合页
- 不把治理、模型看板、患者详情混在同一主内容区
- 不把患者详情误导成“自动已经完成真实预测”
- 不弱化角色权限差异
- 不改变主闭环：登录 -> 工作台 -> 患者详情 -> 真实预测 -> 最新结果 -> 退出登录

## 12. 给 Stitch 的交付目标

Stitch 输出的理想结果应包括：

- 新的信息架构建议
- 业务壳层布局方案
- 登录页方案
- 医生首页方案
- 患者详情方案
- 随访页方案
- 模型洞察 / 模型看板 / 治理页的区分方案
- 关键状态的交互表达方案
- 设计 token 或风格基线建议

## 13. 当前不在本轮范围

以下内容 Stitch 可以知道，但不要作为这次设计重心：

- `/api/me` 问题
- 未挂载的中间件 dead code
- 系统中心深度重构
- 模型训练中心
- CSV 导入治理
- openhis 风格迁移

## 14. 一句话给 Stitch

请把它当成一个“慢病辅助诊疗临床工作站”，而不是一个通用后台，也不是完整医院 HIS。

设计必须围绕真实主闭环、角色分工、患者详情核心页和模型预测状态表达展开。
