# 论文 4.3 数据库设计拆分修订稿

以下内容可替换 `docs/毕设论文原文转写.md` 中的“4.3 数据库设计”部分。修订思路是参考 OpenHIS 的“基础字典表、业务记录表、角色授权表分离”方式，把原来过长的患者主档案表拆成患者主索引、联系方式、建档信息等逻辑表，同时把药品目录拆成药品主数据、剂型、单位、用法、用药记录和药师审核表。

## 4.3 数据库设计

本系统面向慢病辅助诊疗场景，数据库设计不追求覆盖完整 HIS 的收费、住院、医保结算等全流程，而是围绕患者连续管理、医护协同、药事审核、模型辅助和系统治理进行组织。参考 OpenHIS 中“基础字典表、业务记录表、角色授权表相互分离”的设计思路，本文将数据库划分为用户权限、患者档案、病程事件、随访闭环、药事管理、模型结果和审计治理等几个部分。这样既能够支撑系统主要业务功能，也可以避免单张数据表字段过多、职责混杂的问题。

需要说明的是，当前工程实现为了兼顾演示稳定性和历史接口兼容，在 `patients` 等表中仍保留了部分聚合字段；本文在数据库设计中采用逻辑拆分方式进行说明，即把患者基础信息、联系方式、建档信息和临床摘要按业务含义拆开描述。该处理方式与系统后续演进方向一致，也更符合系统设计类论文对数据库表结构的表达习惯。

## 4.3.1 数据库概念结构设计

系统数据库以患者主索引为中心，向外关联病程事件、患者档案、附件资料、当前用药、随访任务、联系记录和模型预测结果。用户、角色和模块权限构成系统访问控制基础，药品目录、剂型、单位、用法等基础字典为药事管理提供支撑。整体关系可以概括为：医生和护士围绕同一患者开展诊疗与随访，药师对医生开立的用药记录进行审核，档案员维护患者档案完整性，管理员负责角色权限、模型治理和系统审计。

从实体关系上看，患者主索引与病程事件、附件、随访任务、联系记录、当前用药、预测结果之间均为一对多关系；药品目录与当前用药之间为一对多关系；角色与系统模块之间通过角色授权关系形成多对多关系。该结构能够支撑患者详情、护士随访、药师审核、模型洞察和治理中心等页面的数据展示。

## 4.3.2 核心数据表划分

参考 OpenHIS 将用户、角色、模块、药品、剂型、单位、用法等信息拆分管理的方式，本文将核心数据表按业务域进行划分，如表4.3所示。

表4.3 核心数据表划分

| 业务域 | 数据表 | 主要职责 |
|---|---|---|
| 用户权限 | `doctor_users`、`roles`、`system_modules`、`role_module_permissions` | 保存账号、角色、系统模块和角色授权关系 |
| 患者档案 | `patients`、`patient_contacts`、`patient_archives` | 保存患者主索引、联系方式、病案建档信息 |
| 病程管理 | `patient_events`、`patient_encounter_state` | 保存时序病程事件和当前接诊状态 |
| 随访闭环 | `outpatient_tasks`、`outpatient_task_logs`、`patient_contact_logs` | 保存随访任务、任务处理日志和联系记录 |
| 电子档案 | `patient_attachments` | 保存患者照片、证件、检查报告、转诊单和知情同意书 |
| 药事管理 | `drug_catalog`、`drug_dosage_forms`、`drug_units`、`drug_usages`、`patient_medications`、`pharmacy_reviews`、`drug_permissions` | 保存药品字典、患者用药、药师审核和药品权限 |
| 模型辅助 | `prediction_results`、`model_run_logs` | 保存预测结果、证据摘要、Top-K 风险和模型调用记录 |
| 审计治理 | `governance_records`、`system_audit_logs` | 保存数据质量问题、治理动作和系统审计日志 |

通过上述拆分，数据库设计既覆盖慢病辅助诊疗系统的主要业务，又避免了单表字段过长的问题。与 OpenHIS 相比，本文系统保留其模块化和字典化设计思想，但没有扩展到收费管理、住院管理、医保结算和手术管理等大型综合 HIS 范围，从而保证系统边界与毕业设计主题一致。
